## 业务场景

实习项目里的"数据下载"弹窗，是我在企业里写的第一个复杂表单。它的需求一句话就能说清楚，但校验规则是动态的：

- 选择测点（多选，至少一个）
- 获取方式二选一：**时间段** / **特定时刻**
  - 时间段模式下：数据范围必填；若数据类型选了"自定义时间点"，时间点列表也必填
  - 特定时刻模式下：数据时刻必填
- 其余：颗粒度、数据值类型、文件格式、工作簿选项……

麻烦在于**必填规则随用户的选择而变**：同一个字段，上一秒是可选的，切个模式就变成必填了。静态校验玩不转这个需求。

这个弹窗的表单校验先后经历了三个版本，横跨我实习的第二到第四周。回头看，它刚好对应我理解 Angular 的三个层次：**双向绑定 → 响应式表单 → 变化检测与响应式状态**。

## V0：ngModel 模板驱动，没有校验

第一周的初版用的是最朴素的写法：

```typescript
dataType = signal<'custom' | '24hours' | 'all'>('custom');
customTimePoints = signal<string[]>([]);
```

```html
<nz-select nzMode="tags"
  [nzDisabled]="dataType() !== 'custom'"
  [(ngModel)]="customTimePoints">
</nz-select>
```

`[(ngModel)]` 双向绑定，简单直接，功能能跑。问题也明显：**没有任何校验**，用户一个测点都不选也能点确定，脏数据直接流下去；而且每个字段的状态散落在各个 Signal 里，提交时想统一检查一遍都费劲。

初版阶段这样写无可厚非——先跑通流程。但它注定要被重构。

## V1：响应式表单 + 动态校验器

第三周重构，核心动作是把整张表单收进一个 `FormGroup`：

```typescript
export class DownloadData {
  private fb = inject(FormBuilder);

  downloadForm = this.fb.group({
    selectedPoints: [[], [this.atLeastOnePointValidator.bind(this)]],
    timeRangeMode: ['时间段'],
    dataType: ['custom'],
    customTimePoints: [[]],
    dateRange: [null],
    dateMoment: [null],
    // ...颗粒度、数据值、文件格式等
  });
}
```

### 动态校验：监听变化，换验证器

动态必填的关键是三个 API 的组合拳：`setValidators` / `clearValidators` / `updateValueAndValidity`：

```typescript
// 监听获取方式的切换
this.downloadForm.get('timeRangeMode')?.valueChanges.subscribe(mode => {
  this.updateValidators(mode);
});

updateValidators(mode: string) {
  const dateRangeControl = this.downloadForm.get('dateRange');
  const dateMomentControl = this.downloadForm.get('dateMoment');

  if (mode === '时间段') {
    // 时间段模式：数据范围必填，数据时刻不管
    dateRangeControl?.setValidators([this.dateRangeValidator.bind(this)]);
    dateMomentControl?.clearValidators();
  } else {
    dateMomentControl?.setValidators([Validators.required]);
    dateRangeControl?.clearValidators();
  }

  // 换了验证器必须手动刷新，否则状态不更新
  dateRangeControl?.updateValueAndValidity();
  dateMomentControl?.updateValueAndValidity();
}
```

数据类型对时间点的影响同理，还叠了一层条件：只有"时间段 + 自定义时间点"同时成立时才校验 `customTimePoints`。

### 自定义验证器

内置的 `Validators` 不够用，自己写：

```typescript
// 日期范围必须是 [起, 止] 都有值
dateRangeValidator(control: AbstractControl): ValidationErrors | null {
  const value = control.value;
  if (Array.isArray(value) && value.length === 2 && value[0] && value[1]) {
    return null;
  }
  return { required: true };
}
```

### 提交：先标记 touched，再校验

提交时把所有字段标成 `touched`（触发红色错误样式），通过了才收数据：

```typescript
submitForm() {
  Object.keys(this.downloadForm.controls).forEach(key => {
    const control = this.downloadForm.get(key);
    control?.markAsTouched();
    control?.updateValueAndValidity();
  });

  if (this.downloadForm.valid) {
    this.handleOk();
    return true;
  }
  // 不通过则按字段给出具体错误提示
  this.showValidationErrors();
  return false;
}
```

模板侧也配套升级：`formControlName` 替代 `ngModel`，`<nz-form-control nzErrorTip="...">` 提供错误提示。到这里，**功能层面已经完整了**。

但这里埋着一个我当时没意识到的问题。

## V1 的问题：模板里的方法调用

为了让"字段标题在出错时变红"这类逻辑生效，我在模板里写了一堆方法调用：

```html
<!-- 每次渲染都要执行方法 -->
<div [ngClass]="getPointsTextClass()">选择要获取数据的测点</div>
<nz-form-control [nzValidateStatus]="getCustomTimePointsStatus()">
```

```typescript
getPointsTextClass(): string {
  const control = this.downloadForm.get('selectedPoints');
  if (control?.invalid && (control?.touched || control?.dirty)) {
    return 'text-[#ff4d4f]';
  }
  return 'text-[#030229]';
}
```

功能正常。**问题在性能。**

## 插叙：Angular 的变化检测为什么会放大这个问题

这是这段实习里我学到的最重要的一课，值得单独讲清楚。

Angular 默认的变化检测策略下，**应用里任何一处事件（点击、输入、定时器、HTTP 回调）都可能触发一轮变化检测，而每轮检测会重新执行模板里的所有表达式**。

也就是说：

- `{{ userName }}` —— 读一个属性，代价可忽略
- `[ngClass]="getPointsTextClass()"` —— **执行一个函数**，函数体里还要 `form.get()` 查控件、读三个状态、做判断

一个用户疯狂操作的页面上，这些方法每秒可能被执行几十上百次，每次都是完整重算。字段一多，开销雪崩。所以官方文档明确把"模板里调用方法"列为反模式——**要么绑定属性，要么绑定 Signal，让框架只在值真正变化时才更新视图**。

我是在和导师讨论之后才真正意识到这一层的。于是有了第四周的两次迭代。

## V2 第一次迭代：封装方法（失败的优化）

第一反应是"把方法写整洁"：抽一个通用入口，按字段名取状态：

```typescript
private shouldShowError(control: any): boolean {
  return control?.invalid && (control?.touched || control?.dirty);
}

getFieldStatus(fieldName: string): string {
  const control = this.downloadForm.get(fieldName);
  return this.shouldShowError(control) ? 'error' : '';
}
```

代码确实干净了，复用也好了。但**模板里调用的还是方法**，变化检测照样每次都执行它们。治标不治本。

这次"失败的优化"反而让我把问题想明白了：**问题不在方法写得怎么样，在于"每次渲染都重算"这个模式本身。要打破它，就得让状态只在真正变化时被计算一次。**

## V2 第二次迭代：Signal 集中状态 + 统一监听

第二版的方案一句话：**把所有校验状态收进一个 Signal 对象，在事件发生时更新它，模板只读它。**

### 1. 状态集中

```typescript
fieldStates = signal({
  selectedPointsTextClass: 'text-[#030229]' as string,  // 出错变红
  customTimePointsStatus: '' as string,                  // ng-zorro 的 error 状态
  dateRangeStatus: '' as string,
  dateMomentStatus: '' as string,
  isTimeRangeMode: true as boolean,                      // 辅助判断也收进来
  isSpecificMomentMode: false as boolean,
  isDataTypeNotCustom: false as boolean,
});
```

### 2. 统一更新入口

```typescript
private updateFieldStates(): void {
  const form = this.downloadForm;
  const shouldShowError = (ctrl: any) =>
    ctrl?.invalid && (ctrl?.touched || ctrl?.dirty);

  this.fieldStates.update(states => ({
    ...states,
    selectedPointsTextClass:
      shouldShowError(form.get('selectedPoints')) ? 'text-[#ff4d4f]' : 'text-[#030229]',
    customTimePointsStatus:
      shouldShowError(form.get('customTimePoints')) ? 'error' : '',
    // ...
    isTimeRangeMode: form.get('timeRangeMode')?.value === '时间段',
  }));
}
```

### 3. 用 RxJS merge 合并所有触发源

什么事件会导致校验状态变化？值变化、校验状态变化、字段被触摸——全部 merge 到一个订阅里：

```typescript
merge(
  this.downloadForm.valueChanges,                    // 值变了
  this.downloadForm.statusChanges,                   // 整表校验状态变了
  this.downloadForm.get('selectedPoints')?.statusChanges || of(),
  this.downloadForm.get('customTimePoints')?.statusChanges || of(),
  this.downloadForm.get('dateRange')?.statusChanges || of(),
  this.downloadForm.get('dateMoment')?.statusChanges || of(),
).subscribe(() => this.updateFieldStates());
```

一个 `subscribe` 替代六七个分散的订阅，逻辑收口。

### 4. 失焦即时反馈

光有状态还不够，用户体验上"失焦立刻报错"比"提交时才报错"好得多。写一个通用的 `onFieldBlur`：

```typescript
onFieldBlur(fieldName: string): void {
  const control = this.downloadForm.get(fieldName);
  if (control && !control.touched) {
    control.markAsTouched();
  }
  this.updateFieldStates();  // 立即刷新，用户马上看到反馈
}
```

不同组件绑不同事件——输入类组件用 `nzBlur`，带弹出面板的日期组件用 `nzOnOpenChange`：

```html
<nz-select formControlName="customTimePoints"
  (nzBlur)="onFieldBlur('customTimePoints')">
</nz-select>

<nz-range-picker formControlName="dateRange"
  (nzOnOpenChange)="$event === false && onFieldBlur('dateRange')">
</nz-range-picker>
```

### 5. 模板只剩 Signal 读取

```html
<div [ngClass]="fieldStates().selectedPointsTextClass">选择要获取数据的测点</div>

<nz-form-control [nzValidateStatus]="fieldStates().customTimePointsStatus">
  <nz-select formControlName="customTimePoints"
    [nzDisabled]="fieldStates().isDataTypeNotCustom"
    (nzBlur)="onFieldBlur('customTimePoints')">
  </nz-select>
</nz-form-control>

@if (fieldStates().isTimeRangeMode) {
  <!-- 数据范围区块 -->
} @else if (fieldStates().isSpecificMomentMode) {
  <!-- 数据时刻区块 -->
}
```

零方法调用。变化检测跑多少轮都无所谓——Signal 没变，视图就不动。

### 两版对比

| 维度 | V2 第一次（封装方法） | V2 第二次（Signal） |
| --- | --- | --- |
| 模板语法 | `[ngClass]="getFieldTextClass('xxx')"` | `[ngClass]="fieldStates().xxxClass"` |
| 执行频率 | 每轮变化检测都执行 | 仅状态真正变化时更新 |
| 状态管理 | 分散在各方法里 | 集中在一个 Signal |
| 加一个字段 | 加方法 + 改模板 | Signal 加一个属性 |
| 失焦反馈 | 有延迟 | 立即 |

## 后日谈：这个思路的延伸

第二阶段（3 月）里，这个"别在模板里调方法"的思路又以两种形态出现过：

**纯管道**。把"状态码 → 颜色 + 按钮权限"的映射逻辑抽成了 `pure` 管道：

```typescript
@Pipe({ name: 'structureStatus', standalone: true, pure: true })
export class StructureStatusPipe implements PipeTransform {
  transform(state: number): StructureViewState {
    // state 不变 → 直接用缓存的计算结果
    return { statusColor, canEdit, canDelete, editBtnClass, editTooltip, ... };
  }
}
```

纯管道的缓存特性和 Signal 异曲同工：**输入不变就不重算**。适合"原始值 → 视图模型"这种纯映射。

**统一校验服务**。把 `markAsTouched` 遍历和错误提示收集收进 `FormValidatorService`，各弹窗一行 `this.formValidator.markControlsAsTouched(form)` 搞定，错误提示还能批量吐出来：

```typescript
this.formValidator.markControlsAsTouched(this.downloadForm);
if (!this.downloadForm.valid) {
  this.formValidator.getFormErrorTips(this.downloadForm)
    .forEach(msg => this.message.error(msg));
}
```

从"每个弹窗自己写校验"到"全项目一套校验服务"，是这段经历里我最直观体会到的**抽象复利**。

## 收获

这一个表单教我的东西，比任何教程都多：

1. **框架的反模式清单要当真**。"模板里别调方法"文档里就写着，不踩一次坑它只是一句话，踩过之后它成了本能
2. **性能问题的正确解法通常是换模式，不是优化旧模式**。第一次迭代的失败让我明白了这点
3. **Signal、纯管道、OnPush 的共同内核**：让"计算"只发生在"依赖变化"的时刻
4. **用户体验是校验的灵魂**：`touched` / `dirty` 的语义差别、失焦即时反馈、提交时统一标红——校验不只是拦截脏数据，更是和用户的对话
