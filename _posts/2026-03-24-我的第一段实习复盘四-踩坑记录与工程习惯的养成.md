## 这一篇讲什么

这个系列的最后一篇，收录那些"不是技术体系、但让我成长最快"的东西：Git 的三连坑、一次白屏排查、和设计稿的博弈、被 code review 的记忆，以及实习期间养成的几个工作习惯。

技术会过时，这些不会。

## Git 三连坑

### 坑一：被 Vim 困住的 merge

第二周在 `version41_dev` 分支上做合并，`git merge` 一敲，终端突然变成了一个我没见过的全屏编辑器——Vim。光标乱跳、按什么都不对、Ctrl+C 没用，提交信息改不了也退不出，整个合并流程卡死。

查了文档才知道：Vim 里要先按 `i` 进插入模式编辑，`Esc` 退出编辑，然后 `:wq` 保存退出。三行命令解决的事，慌了十分钟。

这个坑本身很小，但它教会我一件事：**命令行工具背后还有一整个世界，别只会按回车。** 后来我干脆把默认编辑器换掉了，一劳永逸：

```bash
git config --global core.editor "code --wait"
```

### 坑二：pull 了，但"没完全 pull"

这个坑困扰我最久。症状很诡异：`git pull` 明明执行了，代码也更新了，但 `git status` 里一堆"待提交"的文件——**这些文件云端明明已经提交过了，为什么我本地还显示要提交？** 而且根本分不清哪些是自己真改的，哪些是"假差异"。

后来才明白发生了什么：**本地分支和远端分支的历史分叉了**。`git pull = fetch + merge`，一旦本地有过没 push 的提交（或 merge 中断过、IDE 偷偷格式化过文件、换行符 CRLF/LF 不一致），本地的提交历史就不再"站在"云端的最新提交上。文件内容看起来一样，但 Git 认为你们的历史不是一条线。

当时的解法是后来整理进笔记的"安全重置四步法"，核心思想一句话——**先统一历史，再处理差异**：

```bash
git stash                          # 1. 我的修改全部冻起来（保护现场）
git fetch --all                    # 2. 只更新情报，不动现场
git reset --hard origin/version41_dev  # 3. 宣布：云端历史是唯一正确的
git stash pop                      # 4. 把我的修改放回来
```

走完这四步，剩下的"待提交"文件就只剩真正属于我的修改了；有冲突，那才是真需要人工处理的地方。

日常预防则是改用 rebase 拉取，保持历史线性：

```bash
git pull --rebase
# 或一劳永逸
git config --global pull.rebase true
```

判断口诀也记进了笔记：**"我信云端，还是信本地？"** 信云端 → stash + reset；本地提交重要 → pull --rebase。

### 坑三：把 stash 用成版本管理

第二阶段（3 月）同时改着几块互不相关的功能，工作区总是乱的。我开始用 stash 分版本管理修改：

```bash
git stash list        # 有哪些存档
git stash show -p 1   # 看某份存档的具体改动
git stash apply       # 放回但保留存档（不确定时用）
git stash drop        # 直接删掉（确定不要时用）
```

笔记里给 stash 写了个记忆法：**stash 像回收站——想要 `pop`，犹豫 `apply`，不要 `drop`，全不要 `clear`。**

三个坑连起来看，其实就是一条学习曲线：从"Git 是个同步按钮"到"Git 是一棵可以操纵的提交树"。实习最大的馈赠是逼着我从前者走到了后者。

## 一次白屏排查

第二周的某天，修完一组编译错误（TS2305、NG1010 之类），项目能跑了，页面却一片空白——**控制台干干净净，一个报错都没有**。

没有报错的故障最难查。当时的排查路径：

1. 编译已通过 → 排除语法/引用层问题
2. 从"数据加载"到"模板渲染"整条链路打点，检查 Signal 里的数据流向
3. 最终定位：**数据初始化的时机和模板渲染不同步**——模板渲染时数据还没到，而绑定方式又不会在数据到达后触发更新

调整数据绑定逻辑后恢复。这次的收获是方法论层面的：**没有报错 ≠ 没有问题，链路打点是这种"沉默故障"的唯一武器。** 与其盯着屏幕猜，不如在数据流的每个环节插一行 log，让事实说话。

## 和设计稿的博弈

第二周开发结构物列表时撞上的：设计稿给右侧列表预设了 `736px` 的固定高度。照抄的话，小屏幕溢出、大屏幕留白——因为设计稿是按设计师那块屏幕画的静态快照，而真实页面的高度应该随视口和内容走。

处理方式：

```html
<!-- 废弃：写死高度 -->
<div class="h-[736px]">...</div>

<!-- 改用：高度交给布局上下文 -->
<div class="h-full">...</div>
```

`h-full` 生效的前提是父级 Flex/Grid 容器把高度约束传下来，所以配套调整了整条布局链，最终实现"定宽 + 高度自适应"。

这件事对我的意义超出了一次布局修复：**我开始把设计稿当"需求参考"而不是"施工图"。** 之后每次拿到设计稿，都会先过一遍问题清单：这个尺寸在极端数据下会怎样？列表空了显示什么？文字超长怎么截断？——这些问题设计稿不会回答，但页面必须回答。

## 被 code review 的记忆

第二阶段被导师 review 代码，几条反馈至今记得：

> **"不要在模板中调用方法，使用计算属性、封装对象或信号。"**

这条我在[第二篇](../我的第一段实习复盘二-一个表单校验的三次迭代)里详细写过了——妙的是我在第四周自己踩过一模一样的坑，导师一条反馈直接把"坑"升级成了"原则"。**自己踩坑给你痛感，好的 review 给你原则。两者都遇到是运气。**

> **"获取宽度的方式不严谨，尝试获取父元素的宽度。"**

一行代码的事，但暴露的是"能用就行"的心态。严谨不是抠细节，是尊重边界条件。

> **"这个树状结构，考虑一下是否值得封装为组件。"**

反过来的一面：**不是所有复用都值得抽象**，封装有成本（API 设计、维护、心智负担）。什么时候抽、什么时候忍，是比"会封装"更难的判断。

被 review 的瞬间不好受——每条反馈都是"你以为写完了，其实没有"。但改完之后代码肉眼可见地变好，这种"难受 → 变好"的循环上瘾。现在我对 code review 的态度是主动求虐：**反馈越早到，返工越便宜。**

## 工作习惯的养成

最后盘点这段实习沉淀下来的工作习惯，它们比任何具体技术都保值。

### 1. 每日 TODO + 打勾

每天开工前列当天要做的几件事，做完打 `√`。价值不在"列"，在**打勾时被迫确认"这件事真的做完了吗"**——很多次想打勾时发现还差一点，又回去补了。TODO 是写给自己的最小验收标准。

### 2. 三段式周报

每周按固定结构写：**完成 / 遇到的问题 / 怎么解决的**。"怎么解决的"是最值钱的一段——它逼着我在解决之后回头看一遍，把偶然的尝试整理成可复现的路径。写不出来，说明其实还没真正理解。

### 3. 学习笔记随学随记

Angular 三层架构、Tailwind 布局选型（一维 Flex、二维 Grid、图层 Position）、Git 命令清单、ng-zorro 弹窗配置……全部记成笔记。当下觉得费时间，回头看每次翻笔记都比重新搜快十倍。**笔记是给未来的自己买的保险。**

### 4. 原代码 / 新代码对比存档

重构前把原代码存一份，重构后并排对比，改动点一目了然。这个习惯让"重构"从危险操作变成安全操作——永远知道改了什么、能对着旧版本解释新版本。写这个复盘系列时，这些存档就是最可靠的素材。

### 5. 提交信息说人话

`feat: 错误检校服务`、`fix: 修复列表底部菜单被遮挡`——type 前缀 + 一句话说清做了什么。翻提交历史时，好的提交信息就是项目的编年史。
