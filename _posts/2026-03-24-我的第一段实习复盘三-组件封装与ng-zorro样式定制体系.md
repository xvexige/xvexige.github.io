## 为什么会有这一篇

上一篇讲表单校验，这一篇讲同期并行的另一条线：**怎么和第三方组件库相处**。

用 ng-zorro-antd 这类组件库，迟早会遇到三件事：组件不完全符合设计稿、同样的定制在多个页面重复出现、以及"改了样式却不生效"。我在实习里把这三个坑都踩了一遍，最后落成两个产出：一个**自定义分页组件**，和一套 **`ng-zorro-override.css` 样式覆盖体系**。

## 一、自定义分页组件：第一次正经的组件设计

### 为什么要造轮子

第二周做结构物列表，分页用的是原生 `<nz-pagination>`。用下来三个痛点：

1. **样式定制困难**：默认样式和设计稿差异大，覆盖成本高
2. **功能过于复杂**：一堆我们用不到的配置
3. **每页条数选择器风格不统一**：和项目整体设计格格不入

与其每个页面各自硬改，不如封装一次全局受益。

### 设计三原则

**1. 解耦数据——只收总条数，不收数据数组。**

分页组件只该管"第几页、每页几条"，不该关心也不该持有业务数据。数据切片留在父组件的 `computed()` 里做，组件间传的只有 `total` 一个数字——传引用是零开销的，也不会诱导子组件去做业务计算。

**2. 双向绑定用 Angular 19 的 `model()`。**

```typescript
@Component({
  selector: 'app-custom-pagination',
  standalone: true,
  imports: [NzPaginationModule, NzSelectModule, FormsModule],
  templateUrl: './custom-simple-pagination.html',
})
export class PaginationComponent {
  total = input.required<number>();          // 必传：总条数
  pageIndex = model<number>(1);               // 双向绑定：当前页
  pageSize = model<number>(10);               // 双向绑定：每页条数
  pageSizeOptions = input<number[]>([10, 20, 50, 100]);  // 可选配置
}
```

`model()` 是 Angular 19 的新 API，对比传统写法省掉一整套仪式：

```typescript
// 传统 @Input + @Output：两个成员 + 手动 emit
@Input() pageIndex = 1;
@Output() pageIndexChange = new EventEmitter<number>();
setPageIndex(v: number) {
  this.pageIndex = v;
  this.pageIndexChange.emit(v);
}

// model()：一个成员搞定
this.pageIndex.set(v);  // 父组件 [(pageIndex)] 自动同步
```

**3. 换页容量自动回第一页。**

```typescript
onPageSizeChange(size: number) {
  this.pageSize.set(size);
  this.pageIndex.set(1);  // 否则可能停在一个超出范围的页码，看到空白页
}
```

一个容易被忽略的体验细节。

### 用起来的样子

```html
<app-custom-pagination
  [total]="sortedStructures().length"
  [(pageIndex)]="currentPage"
  [(pageSize)]="pageSize">
</app-custom-pagination>
```

父组件侧配合 Signal，整条分页链路是声明式的：

```typescript
sortedStructures = computed(() => /* 状态排序 */);
paginatedStructures = computed(() =>
  this.sortedStructures()
    .slice((this.currentPage() - 1) * this.pageSize(), ...)
);
```

这个组件后来在项目多个页面复用。第一次体会到：**好的封装不是炫技，是让重复的事只发生一次。**

## 二、ng-zorro 样式覆盖：从打补丁到建体系

### 先踩坑：为什么样式死活不生效

给 ng-zorro 组件改样式，新手期我撞过两堵墙：

**第一堵墙：Angular 的样式隔离。** 组件里写的 CSS 默认带 ViewEncapsulation，作用不到 ng-zorro 渲染出来的内部 DOM。弹窗更是直接挂在 `body` 下，压根不在你的组件树里。

**第二堵墙：组件库自身的样式权重。** ng-zorro 的选择器写得层级很深，你写的简单选择器拼不过它。

解法组合拳：

- 样式统一放**全局样式文件** `src/styles/ng-zorro-override.css`，绕开组件隔离
- 用 `.custom-xxx` 前缀类名限定作用域，避免全局污染
- 必要时**加深选择器层级**（`.custom-modal .ant-modal-header`）
- 关键属性上 `!important`——不优雅，但对组件库是务实的选择

### 从"打补丁"到"建体系"

第三周我发现同样一批覆盖样式在好几个组件里重复出现，每人一份写法还不一样。于是把所有 ng-zorro 的定制收进一个文件，定了四条规范：

1. **CSS 变量管颜色**：边框的默认 / hover / focus / error / disabled 五态全部变量化
2. **`custom-` 前缀管作用域**：想定制就挂类名，不定制不受影响
3. **每个样式块带用法注释**：写清楚在 TS 里怎么用、在 HTML 里怎么挂
4. **状态全覆盖**：hover / focus / error / disabled 一并处理

变量定义长这样：

```css
:root {
  --default-border-color: rgba(225, 226, 233, 1);
  --hover-border-color: rgba(3, 2, 41, 0.70);
  --focus-border-color: rgba(28, 110, 249, 1);
  --error-border-color: rgba(255, 77, 79, 1);
  --error-placeholder-color: rgba(255, 77, 79, 1);
  --disabled-border-color: rgba(250, 250, 251, 1);
}
```

以 Select 为例，一个"完整"的定制要覆盖到四种状态：

```css
.custom-select .ant-select-selector {
  border: 1px solid var(--default-border-color) !important;
  border-radius: 6px !important;
}
.custom-select:not(.ant-select-disabled) .ant-select-selector:hover {
  border: 1px solid var(--hover-border-color) !important;
}
.custom-select.ant-select-focused .ant-select-selector {
  border: 1px solid var(--focus-border-color) !important;
}
.custom-select.ant-select-status-error .ant-select-selection-placeholder {
  color: var(--error-placeholder-color) !important;
}
```

这套体系覆盖了 Modal、Select、Segmented、RangePicker、DatePicker、Tooltip、Pagination、Switch 八个以上的组件。收益直接写在后续开发速度上：新页面挂个 `custom-select` 类就有一致的视觉，换主题色只动变量。

### 两个值得展开的定制案例

**案例一：弹窗高度自适应。** 需求是弹窗顶部留 80px、内容区撑满剩余高度、内部滚动。核心是 Flex 三段式：

```css
.custom-fill-height-modal .ant-modal {
  height: calc(100vh - 80px) !important;
  top: 80px;
}
.custom-fill-height-modal .ant-modal-content {
  height: 100% !important;
  display: flex !important;
  flex-direction: column !important;
}
.custom-fill-height-modal .ant-modal-header { flex-shrink: 0; }
.custom-fill-height-modal .ant-modal-body {
  flex-grow: 1;      /* 吃掉所有剩余空间 */
  overflow-y: auto;  /* 内容多了内部滚，而不是把弹窗撑高 */
}
```

`flex-shrink: 0` 保头脚、`flex-grow: 1` 撑身体、`overflow-y: auto` 兜滚动——这个骨架后来我在很多布局里反复用。

**案例二：带按钮的弹窗标题。** "数据推送"弹窗的标题栏要放一个"协议文档"胶囊按钮，原生 `nzTitle` 只收字符串。解法是 `ng-template` + `TemplateRef`：

```html
<ng-template #titleTemplate>
  <div class="custom-modal-title-row">
    <span class="main-title">数据推送</span>
    <div class="protocol-btn">协议文档</div>
  </div>
</ng-template>
```

```typescript
@ViewChild('titleTemplate') titleTemplate!: TemplateRef<any>;

openDataPush() {
  this.modalService.create({
    nzTitle: this.titleTemplate,  // 模板当标题，随便塞内容
    nzContent: DataPush,
    nzWidth: 1280,
    nzWrapClassName: 'custom-modal custom-fill-height-modal',
    // ...
  });
}
```

**模板引用可以传给配置项**，这个小技巧打开了弹窗定制的天花板。

## 三、组件库满足不了的时候：自己写

第二阶段（3 月）遇到两个"组件库顶不住"的场景，最后都是自己实现的：

**带状态色的下拉选择。** `nz-select` 渲染不了设计稿要的红/绿/灰状态圆点，于是放弃默认组件，用"自定义按钮 + 下拉列表 + 点击外部关闭监听"手搓了一个，圆角、阴影、hover 效果全按设计稿来。这次学到的不是某个 API，而是一个判断：**组件库是效率工具，不是天花板。当它的抽象和你的需求错位时，自己写的成本可能更低。**

**冻结列表格 + 空缺省页。** 项目列表要左冻结列、右冻结操作列、中间横向滚动。实现思路：

- 容器 `overflow-auto` + 绝对定位圈定滚动区
- 内容设 `min-w-[1290px]` 保证不被压缩、触发横滚
- 冻结列用 `sticky left-0` / `sticky right-[19px]` + 阴影制造"柱子"效果
- 列表为空时 `@if (projects().length === 0)` 切到空状态占位页

`sticky` 定位做冻结列，是我这次实习学到的最惊艳的 CSS 技巧——没有它，冻结列得上 JS 监听滚动手动位移，代码量和性能都会难看一个量级。

## 四、其他小专题

顺带记录几个同期的小技术点：

**OpenLayers 地图的初始化时机。** 地图要在 DOM 就绪 + 数据到位后才能初始化，用 `effect` + 标志位控制"只执行一次"：

```typescript
private viewReady = signal(false);
private mapInited = false;

constructor() {
  effect(() => {
    if (!this.viewReady() || this.mapInited) return;
    if (this.structures().length > 0 && this.popup()) {
      this.addStructuresToMap();
      this.mapInited = true;
    }
  });
}

ngAfterViewInit() {
  this.viewReady.set(true);
  this.initMap();
}
```

**操作菜单的智能定位。** 列表底部的菜单往下弹会被滚动容器截断，用 `getBoundingClientRect()` 测边界，动态决定 `top-full`（向下弹）还是 `bottom-full`（向上弹）。DOM API 直接服务交互体验的典型案例。

**弹窗数据传递。** `nzData` 进、`inject(NZ_MODAL_DATA)` 接、`#modal.close(formData)` 出，父组件在 `afterClose` 里收——ng-zorro 弹窗的标准数据闭环。

## 收获

1. **封装的判断标准是"重复"**：同样的逻辑出现第二次，就该考虑抽组件/抽服务/抽样式了
2. **好的组件 API 长在业务上**：`total` + `model()` 的设计不是从教科书抄的，是"父组件最想怎么用"倒推出来的
3. **样式覆盖要有体系**：变量、前缀、注释、状态四件套，让"覆盖组件库"从危险操作变成常规操作
4. **组件库的边界要心里有数**：九成需求用它快速搞定，剩下一成，自己写
